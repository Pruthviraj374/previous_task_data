## 2. The named finding, the fix, and the second finding `ava_review` added

Issue #8, verdict implicit `revise` (Minor, single finding, no adjudication paragraph to strike or add anything — unlike round 1's issue #3).

- **`sound_verifier` (Minor, named).** Every expandable container `tests/vaultgen.py` ever built (`kit.vlt`, its nested `sub.vlt`, `spare.vlt` as a non-expanded raw file) always had at least one surviving entry, so the zero-entry / all-torn case was never exercised, and nothing ever caught that `solution/salvage.py`'s `materialize()` made a container's output directory *unconditionally*, before looking at its entries — leaving an empty, ungraded stray directory for a container whose entries all torn or absent. **Reproduced directly** before touching anything: built a held-out vault via `vaultgen.build_vault`, ran `salvage.salvage()` against it in-process (no Docker needed for this step), confirmed a plain-Python `os.walk`-based tree comparison couldn't see the stray directory either — `walk_tree()`'s own docstring purpose (only regular files and symlinked directories are ever listed) makes a plain empty directory invisible by construction, which is exactly the exposure the finding named.

  Fix: `build_vault`'s `hard=True` path now adds two more containers under `/media/bundles/` — `all_torn.vlt` (one entry, torn) and `empty.vlt` (zero entries) — exercised only in the held-out vaults built fresh at verify time (the seeds live in `tests/`, never reachable from the agent image), so the already-frozen shipped vault under `environment/data/vault` is untouched. `test_outputs.py` adds `assert_no_stray_container_dirs()`, called from both held-out test functions, checking directory *non-existence* directly via `os.path.exists` rather than the tree walk. `solution/salvage.py`'s `materialize()` drops the unconditional `os.makedirs()` before the entry loop — a container with surviving entries still gets its directory implicitly, from those entries' own `os.makedirs(os.path.dirname(dest))` calls a few lines below, so this only changes the zero-entry case.

  **Verified before pushing** across the exact three pinned seeds (`HELD_OUT_SEEDS = (713591249, 1902337811)`, `NAMED_SNAPSHOT_SEED = 486022367`) plus several extra random seeds, confirming: (a) the vault generator's 4000-attempt grid/parity constraint solver still converges with two more small chunk-bearing files in the mix, (b) both stray directories are gone post-fix, (c) `kit.vlt`/`sub.vlt` (containers that do have surviving entries) still materialize correctly, and (d) the already-frozen shipped vault's report/tree are byte-identical to `tests/expected` (unaffected, since nothing regenerates it).

- **`sound_verifier` (Minor, unnamed — surfaced by `ava_review` on the first push).** `ava_review`'s "Constructed bypass attempt" analysis noticed that every shipped-vault test (`test_snapshot_defaults_to_the_last_snap_record` and siblings) reads `/app/out` exactly as the agent's own instructed one-shot run (`python3 /app/salvage.py /app/vault /app/out`, per `instruction.md`'s last line) left it — nothing re-invokes the CLI against the shipped vault the way `run_cli()` already does for the two worked examples, both held-out vaults, and the named-snapshot case. `ava_review`'s own text: *"a verifier faithful to the instruction would regenerate /app/out from salvage.py and compare that... exposure is limited to low[-severity]"* — it graded this **Blocking** regardless of its own low-exposure caveat.

  This finding is entirely pre-existing (nothing in the round-2 diff touches this code path) and outside issue #8's checklist, but it gated the PR on the very first push, so it had to be fixed in the same PR per §6's framing, not deferred or argued in a comment (round 1 §5 already burned a cycle on exactly that mistake for a different gate).

  Fix, additive only: `test_cli_regenerates_the_shipped_vaults_own_answer()` re-runs the submitted CLI fresh, into a `tempfile.TemporaryDirectory()` the agent never touched, and asserts the result matches `EXPECTED_REPORT`/`EXPECTED_TREE` exactly — closing the gap the same way the held-out/example checks already do for every other vault, without touching or removing any of the existing "as the agent left it" tests (which remain valid: `instruction.md` does ask for both a working tool and a pre-run `/app/out`). Verified locally via the same subprocess invocation `run_cli()` uses, against the shipped vault, before pushing.

The distinction from `rework-rule.md` §5's b904c71 case matters: there, `pass@5` landed at a *repeated, measured* ~35-40% true failure rate below the ≥60% (3-of-5) bar, and the corpus's own math showed a bare re-roll clears that bar only ~25-30% of the time — a real losing bet. Here there was no repeated pattern (the prior push's pass@2 had already come back clean) and no measured failure rate to bet against — one of the two trial slots was an **in-progress timeout**, a bucket the platform's own pass@5 arithmetic (documented in `platform-rework-docs.md`'s `dynamo-360bee9` note) explicitly counts toward **neither** side. A single such slot makes the sample size effectively 1, which is not decisive evidence of anything. The gate's own text — "Rerun Recommended: YES" — is the platform saying exactly this, not a judgment call this session had to make from first principles. Close/reopen (no commit) drew a fresh, decisive pair.

**Second-order lesson, restated from round 1's note (`REWORK-e843ed4-vault-salvage.md` §3) but worth reconfirming**: pass@2 gated *before* `ava_review`/`deep_review`/`qc_*` even attempted to run on the timeout-inconclusive push (everything downstream showed `skipping`), but ran the full remaining chain once pass@2 came back decisively `0/2` on the re-trigger. A push whose pass@2 result is itself inconclusive buys nothing on the soundness gates that round — don't read a `skipping` status there as "already passed," it means "never reached."

## 6. Dead ends and roads not taken

- **Perturbing `kit.vlt`'s own entries to make it all-torn.** `kit.vlt` already carries a different `sound_verifier` trap (a duplicate-path-wins case) and its chunks feed a diagonal-parity-victim candidate pool (`vaultgen.py`'s `candidates = list(file_chunks["/archive/spare.vlt"]) + ids`). Reusing an existing container for the new all-torn case would have coupled two independent test purposes into one fixture and risked silently breaking the existing trap. Two new, separate small containers were cheaper to add and to verify in isolation.
- **Making `all_torn.vlt`/`empty.vlt` part of the shipped, frozen vault** rather than the held-out-only generation path. Doing so would have required regenerating `environment/data/vault` and `tests/expected/**` — an agent-visible fixture change, which round 1's §8 already flagged as the wrong move on this task (two prior closed attempts on this repo died on pass@2 after touching agent-visible surfaces). The held-out path already runs the exact same `build_vault(hard=True)` code, so the new coverage is real without any fixture churn.
- **Arguing the `ava_review` finding's low-severity caveat in a PR comment instead of fixing it.** `ava_review`'s own text said "exposure is limited to low" — a temptation to treat as advisory. Round 1 §5 already recorded that a QC item filed under "needs human review" (a similarly hedged severity signal) is still a required fix that a comment does not satisfy; the same logic applied here to a **Blocking**-labeled `ava_review` item regardless of its own hedged language, and the fix was three lines of test code, cheaper than a comment-and-wait cycle would have cost anyway.

## 7. Reusable checklist for the next rework

1. Reproduce the named finding directly (in-process, no Docker needed if the tool exposes a plain function) before writing any fix — confirms the exploit and gives you a before/after pair for the PR body.
2. Expect `ava_review`/`deep_review` to surface findings the issue never named, especially on a task's first-ever full re-audit since a prior merge. Fix them in the same PR if they gate — §6's guidance, not §2's scope discipline, governs this case.
3. Read a pass@2/pass@5 "fail" or "block" comment's own diagnostic text before assuming it's a difficulty result. `Rerun Recommended: YES` plus an `in-progress-timeout` bucket entry means the platform itself is telling you this trial produced no signal — re-trigger via close/reopen, don't edit content chasing a result that was never real.
4. Distinguish a *repeated, measured* sub-threshold failure rate (§5's b904c71 case — a real losing bet to re-roll) from a *single inconclusive* trial (this round's case — re-rolling costs nothing and the platform recommends it outright).
5. When adding coverage for a case a generator never produced, check whether it can be added to the **held-out-only** generation path before touching a frozen, agent-visible fixture — cheaper, and avoids re-triggering a difficulty review for a verifier-only fix.
6. `os.walk`-based tree comparisons are blind to plain empty directories by construction (they only enumerate regular files and, deliberately, symlinked directories) — a soundness check for "nothing extra was left behind" needs a direct `os.path.exists` assertion at the specific path in question, not a set-equality check against a walked tree.
